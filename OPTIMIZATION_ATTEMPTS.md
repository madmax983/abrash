# Optimization Attempts Report

## 1. SIMD Textured Scanline (Nearest Neighbor)

**Goal**: Accelerate `rasterize_scanline_textured` for `FilterMode::Nearest` using AVX2.

**Implementation**:
- Implemented `rasterize_scanline_textured_simd_nearest` using `_mm256_i32gather_epi32` to fetch pixels from the texture.
- Used `_mm256_blendv_ps` / `_mm256_blendv_epi8` for masked writes to Z-buffer and Framebuffer.
- Integrated into `src/tile_renderer.rs`.

**Result**: **Regression (2.7x slower)**
- Baseline (`fill_cube_tiled_textured`): ~320 µs
- SIMD Implementation: ~865 µs

**Analysis**:
- The latency of `vpgatherdd` (`_mm256_i32gather_epi32`) is significantly high on the target architecture (likely Haswell/Broadwell generation in VM).
- The overhead of setup (calculating vectors for `u`, `v`, offsets) and the gather instruction outweighs the benefit of processing 8 pixels at once, especially since the scalar loop is tight and efficient (L1 cache hits).
- For small span sizes (max 16 pixels in `TileRenderer`), the startup cost of the SIMD loop is not amortized.

**Conclusion**: Reverted changes. Future optimization should focus on:
- Ensuring data locality (swizzled textures) if gather is used.
- Exploring AVX-512 gather if available (hardware dependent).
- Optimizing `Bilinear` filtering where arithmetic intensity is higher (masking load latency).

## 2. Parallel Object Rendering in Scene

**Goal**: Parallelize the object iteration loop in `Scene::render` using Rayon.

**Implementation**:
- Used `par_iter()` on `self.objects`.
- Performed culling and vertex transformation (`transform_points`) in parallel.
- Collected triangles using `flatten().collect()`.

**Result**: **Regression (~3% slower)**
- Baseline (`render_scene_optimized`, 1000 cubes): ~1.58 ms
- Parallel Implementation: ~1.63 ms

**Analysis**:
- The workload per object (culling + transforming a small 8-vertex cube) is too small (< 2 µs).
- Thread dispatch and synchronization overhead (Rayon `par_iter` + `collect`) exceeds the computation time saved.
- `Vec::push` in the scalar loop is extremely fast (amortized O(1)). Parallel collect involves allocating and merging vectors.

**Conclusion**: Reverted changes. Parallelism at the object level is only beneficial if:
- Objects have high vertex counts (thousands of vertices).
- The number of objects is massive (>> 1000) to amortize thread pool overhead.
- `transform_points` is computationally expensive (e.g., complex vertex shaders).

## 3. SIMD Z-Buffer Clear

**Goal**: Optimize `ZBuffer::clear` which fills the depth buffer with `f32::INFINITY`.
This function consumes ~25% of the frame time in `object_culling` benchmark.

**Implementation**:
- Implemented `clear_avx2` using `_mm256_storeu_ps` in an unrolled loop.
- Benchmarked against standard `slice::fill`.

**Result**: **No Improvement**
- 1080p: ~444 µs (SIMD) vs ~441 µs (Scalar/std).
- 4K: ~3.27 ms (SIMD) vs ~3.19 ms (Scalar/std).

**Analysis**:
- The standard library's `slice::fill` implementation is already highly optimized (likely using `memset` logic or vectorized loops generated by LLVM).
- Since memory bandwidth is the bottleneck for clearing large buffers, manual AVX2 stores do not provide additional throughput over what the compiler/std lib achieves.

**Conclusion**: Reverted changes. Using `slice::fill` is optimal and safer.
